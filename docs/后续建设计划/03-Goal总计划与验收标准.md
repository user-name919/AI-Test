# Goal 总计划与验收标准

编排日期：2026-10-03。性质：实施计划，未启动实施。基线：本地整合提交 `99eee49`；执行前以实际 Git 状态复核。

## 目标

交付一个可视化的企业 B 端测试平台，具有两个核心入口：需求驱动测试、代码变更回归。将需求理解与用例设计建设为可以单独使用的核心模块，先提高用例依据、语义和可验证性，再提高真实浏览器执行的可靠性。

用例设计模块可以在没有测试环境、没有源码连接时完成材料分析、用例审核、版本发布和导出。浏览器环境仅是执行阶段的必要条件；源码和页面探索可增强分析，但不能取代需求和人工最终决定。

## 约束与决策

- 根目录 `web/`、`api/`、`packages/contracts/` 的 monorepo 方向不变。沿用 Vue、Node HTTP、SQLite、Playwright；不另建微服务。
- 仅分析本机已有分支/提交；被测项目由用户部署。不修改 lvworkbench，不切换其当前工作区；目标版本用受管理 worktree 读取。
- 相关用例沿用同一会话与当前 Page；普通失败记录后继续，后续用例独立验证，不继承前序通过结论。
- 不做敏感信息检测与脱敏、多 Agent、跨项目 Manifest 发布。Skills 由平台模型调用链加载，不等于安装开发 IDE 插件。
- AI 可选择测试方法、候选数据和现场动作；不能自行放宽已确认业务预期。
- 按模块进行必要测试和手工验收，不要求每次提交严格全量回归。最终两个核心流程必须有运行证据。
- 历史分析、人工审核版本、执行事实不可覆盖；新分析或重跑产生新版本/记录。
- 凭据、登录态、真实 PRD、源码软链、运行产物不提交到公开仓库。评估样本使用合成或已明确可公开的材料。
- 不自动部署、不默认引入付费云浏览器、不为完成测试购买服务。普通研发选择自主推进；需要新的真实账号/数据/部署才请求用户提供。

## 开源采用策略

| 来源 | 采用内容 | 首轮方式 | 不作为本轮承诺 |
|---|---|---|---|
| Agent Skills 规范 | 明确适用条件、按需读取、案例资源 | 自建三个平台 Skill，记录版本/hash | 全功能插件市场、任意脚本执行 |
| Playwright Test Agents | 可审阅的计划、执行准备、现场验证、修复记录 | 借鉴阶段和产物，仍用单模型顺序流程 | 原样移植多 Agent、自愈自动改业务断言 |
| Stagehand | 观察/提议/操作分离，限定区域、结构化提取 | 改造现有 observer/registry/executor | 更换整个执行引擎 |
| Browser Use | 模型与动作分开超时、有限恢复、历史管理 | 补全现有循环和可见状态 | 新增 Python 浏览器运行栈 |
| Allure Report | 独立尝试记录、附件、历史和故障分类 | 借鉴数据模型和 UI，先保留本站报告 | 托管 TestOps、全量嵌入报表系统 |
| Promptfoo | 样本对比、规则断言和辅助模型评分 | 开发期质量评估，适配现有模型客户端 | 仅凭模型评分自动批准用例 |
| Docling | 表格、布局、OCR 与文档结构 | 独立可选对比实验 | 不经实测替换现有 PDF 解析 |
| Midscene | 视觉定位、视觉证据和报告 | 独立可选对比实验 | 视觉判断替代所有确定性断言 |
| Storybook / Playwright 截图比较 | 组件状态、交互、审核过的截图基线 | 有现成入口时接入；没有则记录后续扩展 | 自动为被测项目搭建组件环境或部署旧版本 |

正式采用依赖前核对所选版本、许可、公司模型协议、本地运行要求和新增成本。官方页面的能力描述不是公司场景已验证的效果。

## 阶段与完成条件

G 编号是新的执行顺序；Q 编号是 04 的用例质量任务；T 编号指向 02 的已有任务。按依赖顺序执行，无需每个阶段都重新问是否继续。

| 阶段 | 内容与任务来源 | 必须交付的验收证据 |
|---|---|---|
| G0 现状与语义修正 | Q0；核对 T00，修正生成器及问题关联 | 人工修改后的契约确实传入模型；无关问题不进入该用例断言；页面就绪原因与服务端一致 |
| G1 工程基础 | T01–T03；保留 G0 修复 | monorepo 可启动；既有数据/产物可读；稳定 case ID；路由与 API 模块边界明确 |
| G2 独立用例生成 | Q1–Q4，整合原 T05 生成约束 | 文档证据 → 需求事实 → 场景覆盖 → 用例草稿 → 审查产物分别保存；局部重跑不覆盖人工结果 |
| G3 用例设计工作台 | Q5 + T04 + T08 材料/审核部分 | 可独立导入、理解、编辑、发布和导出；完整用例/依据可见；无需环境也能完成 |
| G4 质量评估 | Q6，Q7 中 Docling 对比可选 | 固定样本、旧/新输出和问题分类可比较；模型评估与人工验收状态分开 |
| G5 需求自动化闭环 | T05 运行时数据/预检 + T06–T08 + Q8 | 连续会话、失败继续、刷新找回、逐用例完整报告；动态与固定模式消费同一契约版本 |
| G6 变更回归闭环 | T09–T11 | 三个本地提交可形成固定范围；影响建议、人工范围、用例和环境对应版本可追溯 |
| G7 能力与交付 | T12–T13；Q7 Midscene 对比可选 | 核心 B 端缺口按矩阵验证；两个场景完整验收；使用文档与遗留清单准确 |

按用户最新要求，只启动一次 Goal，目标覆盖 G0–G7 全部核心阶段。阶段是执行顺序与验收检查点，不是提前结束整个 Goal 的理由。05 提供唯一的完整启动指令；完成一个阶段后按依赖自主继续，实际外部阻塞须准确记录并处理。

## 核心验收故事

### A：用例生成与人工修改

输入含模糊搜索、高亮和空结果规则的合成 PRD，并附一份存在冲突的技术说明。平台标明材料来源与冲突，生成完整名称、部分名称和无匹配场景；未规定的内容显示待确认，不自动补业务规则。用户从右侧用例跳到左侧原文，修改部分搜索的预期并保存；重新生成该场景只产生建议差异。发布版本后，导出的用例与执行预览保持一致。

### B：真实页面连续测试

打开选择器，从实际 option 提取数据，验证完整/部分/无匹配三类场景各自的数据策略。人为设置一条错误预期，使其失败后下一条仍执行。关闭预览、刷新页面后可找回同一任务；报告保留第一次失败、恢复尝试、后续结果和数据来源。不得以真实产品可用为理由将错误预期改成通过。

### C：本地重构回归

在临时示例仓库构造三次相关提交，其中一个共享组件被两个页面使用；对比模式和目标 SHA 固定保存，能看到受影响页面及无法解析的依赖。人工排除一项风险并写原因，修改一条建议用例；执行关联部署确认，失败报告可返回变更证据。分支移动后旧报告不改变。公司真实环境验收在用户已提供匹配部署时执行。

## Goal 运行记录与停止条件

维护 `docs/后续建设计划/执行进度.md`：当前阶段、基线 SHA、完成任务/提交、验证命令和结果、已确认问题、下一步、外部依赖。开始下一轮先读记录，再核对代码；不要靠对话记忆重复开发。

用户已授权本地 commit。每个独立功能完成并通过相关验证后立即单独提交，不混合无关功能，不等整个阶段完成再统一提交，无需逐次询问许可。标题与正文使用中文，详细描述解决的问题、实现内容、关键设计或兼容性影响、实际验证结果和未验证限制；只暂存该功能相关文件。提交 SHA 写入执行进度。默认不自动推送远端；不要把之前首次上传空仓库的授权理解为以后无限制更新 main。

只有需要新增业务决定、真实账号、不可得依赖或部署时暂停依赖工作，继续可独立完成的任务。中断时保存证据和准确的下一步，不伪称完成。不要重复安装失败依赖或无界重试同一模型/网络错误；区分环境阻塞与代码缺陷。

阶段结束报告四件事：已实现什么、验证到哪一层、尚未验证什么、下一阶段依赖。未运行公司模型/真实业务页时，明确写“本地夹具已验证，真实集成待验收”。
