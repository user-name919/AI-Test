# 用例设计与开源能力任务包

执行顺序见 03。Q0 使用当前路径；G1 迁移后 Q1–Q8 使用目标 monorepo 路径。若实际路径不同，先在执行进度中记录映射，禁止再复制出第二套实现。

## 输入输出约定

复用现有 `CaseExecutionContract`，增加可追溯外层，不将浏览器 locator 固化进业务用例。

```ts
type EvidenceOrigin = 'document' | 'human' | 'source_code' | 'runtime'
interface EvidenceRef {
  documentId: string
  blockId: string
  quote: string
}
interface DocumentBlock {
  id: string
  documentId: string
  kind: 'heading' | 'paragraph' | 'table' | 'image_placeholder'
  page?: number
  section?: string
  text: string
  warnings: string[]
}
interface RequirementFact {
  id: string
  statement: string
  kind: 'explicit' | 'inferred' | 'unresolved'
  evidence: EvidenceRef[]
  relatedQuestionIds: string[]
}
interface ScenarioDraft {
  id: string
  factIds: string[]
  questionIds: string[]
  title: string
  testIntent: string
  coverage: 'positive' | 'negative' | 'boundary' | 'state_transition'
}
interface CaseDesignDraft {
  id: string
  scenarioId: string
  factIds: string[]
  questionIds: string[]
  contract: CaseExecutionContract
  verification: 'browser' | 'api' | 'manual'
}
interface DesignIssue {
  id: string
  targetId: string
  kind: 'missing_evidence' | 'contradiction' | 'missing_coverage'
    | 'invented_data' | 'unverifiable' | 'duplicate'
  severity: 'blocking' | 'warning'
  reason: string
  evidence: EvidenceRef[]
  checkedBy: 'rule' | 'model' | 'human'
}
```

`EvidenceOrigin` 用来区分补充上下文来源；`EvidenceRef` 专门定位文档片段。源码证据复用项目 Provider 的 path/line/commit 结构，运行证据复用 snapshot 和 bindings，不伪装成文档引用。人工决定使用 Review revision 单独关联。

覆盖口径：分母为用户确认纳入范围的显式规则；展示规则→场景→用例映射、无用例的规则、有多个关联的用例和人工排除原因。该映射表示设计覆盖，不证明测试已通过或需求绝对完整。

2. 为用例新增显式 question IDs；新用例按关联问题阻塞/追加断言。旧记录缺少映射时沿用兼容规则并在 UI 标注“历史关联待复核”，不猜测精确映射。

**提交：** `fix: 统一生成计划与人工用例语义`。这一小范围修复在 monorepo 前完成，不借机大拆 App.vue。

## Q1：建立文档证据层与可恢复的生成任务

**依赖：** G1。**文件：** `api/src/modules/case-design/{documents,jobs,repository,routes}.ts`、`packages/contracts/src/case-design.ts`、存储迁移。

- [ ] 保存 document ID、内容 hash、版本、角色和 blocks；同名文件也必须有独立 ID。原文仅本地保存，不把真实材料写入 Git。
- [ ] Markdown 以标题/段落建块；PDF 保留页码和提取警告；图片/复杂表格不可读时形成警告，不假装已解析完整。暂不强制 OCR 依赖。
- [ ] 新增 `POST /api/case-designs` 创建草稿，`POST /api/case-designs/:id/runs` 启动阶段，`GET /api/case-designs/:id` 返回任务和最新产物，`POST /api/case-designs/:id/cancel` 取消。
- [ ] 阶段采用 `extracting / modeling / planning / generating / checking`，运行状态采用 `queued / running / completed / failed / cancelled / interrupted`；返回最近更新时间与错误原因。进程内有界队列，UI 断开不取消。
- [ ] 各阶段保存输入版本/hash、模型配置标识、prompt 版本、Skill 版本/hash、输出和调用统计；输出格式修复不等于语义审核通过。
- [ ] 重启将遗留 running 标为 interrupted；重试生成新 attempt，从已确认兼容的上游结果继续，不能继续使用已改变文档的旧事实。

**验收：** 两份同名文档可区分；多页 PDF 的证据能定位页码；关闭/刷新仍可查看任务；失败保留上游产物。对应最小数据库迁移/状态测试通过。

**提交：** `feat: 保存需求材料证据与分阶段生成任务`。

## Q2：需求事实与场景覆盖先于用例文本

**文件：** `api/src/modules/case-design/{fact-extractor,scenario-planner,evidence-validator}.ts`、提示词资源与对应测试。

- [ ] 抽取规则、角色、输入条件、状态变化、未确定项；每条显式事实必须关联存在的文档块与摘录。
- [ ] 摘录匹配采用明确的空白归一化校验，不把存在同一个关键词当作完整依据；通过匹配也不代表蕴含关系已正确，语义仍需审核。
- [ ] 文档冲突生成问题并保留双方来源，不按文件顺序默认后者覆盖前者。
- [ ] 场景设计使用已提取事实，按适用的等价类、边界、状态转换或决策条件分析；取消“每个需求必须 6–12 条”的硬数量要求。
- [ ] 每条场景带 factIds/questionIds；不确定场景允许保留为建议，不能默认为已确认要求。
- [ ] 大文档按块与章节分批，保存处理清单并最终合并去重/检查跨章节冲突；未处理部分明确列出，不因截断声称全部完成。

**验收：** 缺失页码/章节内容被明确提示；仅写“支持模糊搜索”的材料不会自动规定大小写规则；规则遗漏在覆盖视图可见。

**提交：** `feat: 基于文档依据建立需求事实和测试场景`。

## Q3：三个平台内 Skills 与按需加载

- [ ] `requirement-facts`：区分事实、推断、缺失；关联来源；冲突保留，不代替用户选择业务规则。

- [ ] `case-quality-review`：检查事实依据、可观察预期、缺失条件、重复、步骤矛盾；给建议，不自动修改人工最终口径。

- [ ] 技能是方法指导，规范 JSON 和引用完整性仍由代码校验；不能仅增加 SKILL.md 文件却没有模型加载调用点。

**验收：** 捕获模型请求证明对应阶段实际加载技能；无关技能不进入上下文；同一样本能记录有/无技能的配置用于 Q6 对比。

**提交：** `test: 建立用例生成质量评估基线`。

## Q7：开源能力对比实验（非核心阻断项）

**文件：** `experiments/{docling,midscene}/`、`docs/后续建设计划/开源接入对比结果.md`。实验依赖隔离，不默认进入生产启动链。

- Docling：选择至少 3 个表格/多栏/扫描件样本，对比现有解析的字段配对、来源定位、遗漏、耗时和资源。结论可为采用、部分采用或不采用；保留失败样本说明。没有可用依赖/模型时记未验证，不用猜测替代效果。
- Midscene：选择卡片入口、相似控件、关键词高亮三种场景，核对公司 API 图片输入支持后，与现有 DOM 路线比较。记录误定位、断言证据、耗时和调用量，不只记录最终成功。
- 不因单次成功改变生产默认；只有明确受益且可以保持本地/公司模型要求时，通过单独适配器接入，并保留原路径。实验需要超出现有授权的付费服务时暂停该实验。

**验收：** 有可重现步骤和实测结果或准确的阻塞原因；不编造成功率。可选实验未完成不阻止主功能交付，但不得标为已接入。

## Q8：观察、恢复、报告保持业务语义

**依赖：** G5 的任务框架。**文件：** `api/src/automation/`、`modules/executions/`、`web/src/features/executions/`。

- [ ] 参考 Stagehand 将局部观察、结构化候选、动作提议、执行前引用校验连起来；截图按需补充，缺失视觉证据时不猜。
- [ ] 参考 Browser Use 把模型请求失败、控件操作失败和业务断言失败分开。每种恢复有次数和时间上限；面板显示当前阶段与最近更新时间。
- [ ] 允许重新定位、重新观察、在明确状态下调整等待；对有副作用的提交动作先确认是否已经完成，不能盲目重复提交。
- [ ] 不修改业务预期、不删除断言、不替换为更容易通过的数据。若恢复要改变已确认语义，记录待审核建议，当前结果按实际失败/受阻保存。
- [ ] 参考 Allure 保留 attempt；首次失败、重试结果、最终状态分别存在。稳定复用只缓存候选流程，环境/版本/页面不符时失效，不缓存数据事实与通过结果。
- [ ] UI 展示来源版本、实际数据、规则引用、恢复原因和证据；导出报告与页面使用相同存储结果。

**验收：** 控件 DOM 改变可重新定位，但故意错误的业务预期不能被“修复”为通过；失败继续下一条，历史可回看；上传等副作用操作不被无限重试。

**提交：** `feat: 保持业务语义的有限恢复与证据报告`。
