# 人工 Review 与执行契约

## 为什么不能直接执行人工文字

人工口径通常是业务结论，不一定包含可定位的控件、触发条件或可验证结果。例如“失败时给老师明确提示并支持重试”能够表达意图，但不能直接转换成 `click`、`expectText` 或按钮状态断言。系统必须先把口径解释成结构化规则，再交给 Playwright。

## 两层信息模型

| 信息 | 来源 | 是否可修改 | 用途 |
| --- | --- | --- | --- |
| AI 建议 | PRD / 技术方案分析 | 否 | 保留模型原始判断，便于对照 |
| 人工最终口径 | 产品或测试人员 | 是 | 作为最终业务依据 |
| AI 执行契约 | 人工口径 + PRD + 用例 + 源码 | 可重新生成 | 转换为可执行行为和断言 |

## 执行流程

```text
编辑人工最终口径
  ↓
AI 结合 PRD、原 AI 建议和测试用例
  ↓
按需调用软链项目 Provider
  ├─ 根据 URL 查路由
  ├─ 读取路由和页面组件局部源码
  └─ 把源码线索标为待回到页面验证的依据
  ↓
生成执行契约：触发条件、页面行为、断言、禁止行为、不确定项
  ↓
人工检查执行契约并确认
  ↓
Agent 观察真实 DOM，映射 elementRef 和 Playwright 动作
  ↓
执行后重新观察 DOM，验证所有必需断言
```

## 安全边界

- 源码只辅助理解，不直接当作页面事实。
- 人工口径不直接变成 JavaScript 或任意选择器。
- 执行契约存在 `uncertainties` 时，相关用例继续阻塞，不能让 Agent 猜测。
- `accepted` 和 `edited` 才能解除用例阻塞，`deferred` 只保存记录。
- 每次执行目标都会携带人工口径、执行契约断言和禁止行为，Trace 中仍保留真实 DOM 和动作轨迹。

## 示例

人工口径：

> 报告生成失败时告诉老师原因，保留填写内容，并允许点击重试。

执行契约可能包含：

- 触发条件：报告生成接口返回失败；
- 页面行为：展示失败提示、保留表单内容、重试按钮可用；
- 可验证断言：失败提示可见、重试按钮可操作；
- 禁止行为：不能重复创建任务、不能清空用户输入；
- 源码线索：页面错误处理组件和重试方法，最终仍以真实 DOM 为准。

如果模型无法确认失败文案、重试是否会重复提交等关键事项，会写入“不确定项”，要求人工补充后才能进入执行。
